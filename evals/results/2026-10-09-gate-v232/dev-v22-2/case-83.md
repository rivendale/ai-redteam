## NEEDS VALIDATION

- **S1. Write gate on the tool-call path.** Not supplied. The fact that settles it: does the agent code that calls tools restrict `update_ticket`? Specifically: an allowed set of `status` values, human approval for comments, and whether comments are visible to the customer. The schema gives `status` and `comment` as free strings with nothing required (`approved_tools.json`, `update_ticket`). Without a gate, text in a customer's ticket can steer the agent into closing the ticket or posting promises under the operator's name.
- **S2. Where the token scope is enforced.** context.md says the scope is "enforced by each server". The fact that settles it: is it the backend API that rejects out-of-scope token use, or the `@acme/*-mcp` process? If it is the MCP process, the docs-only and one-ticket limits are only as trustworthy as that npm code, which raises F1 and F2.
- **S3. Do the lock hashes match what was reviewed?** Settle it by computing `sha256(json.dumps(tool, sort_keys=True))` for each entry in `approved_tools.json` and comparing with `tools.lock`. Then confirm the 2026-09-20 review covered exactly these definitions, including any extra fields the server returns, such as `annotations`.
- **S4. Does the check ever fail?** Settle it with a test that changes one character in a listed description and expects a `RuntimeError`.

## REFUTED

- **Tokens leak across servers.** Refuted: `env` is built fresh with only `PATH` and that server's own `TOKEN` (`client.py:35`).
- **Extra or missing tools pass the check.** Refuted: names are compared as sets in both directions, and every listed tool's hash is checked. An unknown server gets an empty approved set and fails if it lists anything (`check_tools`).
- **Drift from the request.** Refuted: all three offered tools are approved, which matches "every tool they offer".

## WHAT HOLDS UP

- The approval check fails closed on renamed, added, removed or edited tools. It hashes the whole definition, so a description-only change ("rug pull") is caught at startup.
- Each server gets only its own token.
- Versions are pinned exactly in `package.json`.
- The tool descriptions contain no text aimed at the model or the reviewer.
- `update_ticket` takes no ticket id, which matches the one-ticket scope.

## UNVERIFIED CLAIMS

- **Lockfile has exact versions with integrity hashes.** Partly contradicted by F1. Confirm with `npm ci` and `npm view @acme/tickets-mcp@1.9.0 dist.integrity`.
- **Token scopes are enforced.** Confirm by calling the backend directly with each token, outside the MCP server, on another ticket or path.
- **The tools were reviewed on 2026-09-20.** Confirm per S3.

## QUESTIONS FOR THE AUTHOR

1. How does the agent get tool definitions and send `tools/call`? Is any of it checked against `tools.lock`?
2. Does the backend or the MCP process enforce the token scopes?
3. Is `update_ticket` gated at all: allowed statuses, approval, comment visibility?

## DECISION-MAKER SUMMARY

Do not turn on ticket write access until three things are done: the lockfile is regenerated by npm (F1), the agent is limited to the checked tool list (F2), and S1 and S2 are answered. If you proceed anyway, unpinned dependencies or an unchecked second tool list can change what the agent does with the operator's credentials on customer tickets, and nothing will flag it.

## OWNER SUMMARY

The check that blocks unapproved tools works when the agent starts, but the agent does not keep using the list it checked. The file meant to pin the exact software versions looks hand-made, so it may not protect anything. Before the agent can change customer tickets, regenerate that file, limit the agent to the checked tools, and confirm who enforces the one-ticket limit.
